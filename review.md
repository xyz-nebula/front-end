## Краткий вывод

Репозиторий не выглядит заброшенным: TypeScript строгий, приложение разбито на
маршруты и сервисные адаптеры, generated-файлы в основном правильно исключены
из Git. Главная проблема сейчас — не объём исходников, а отсутствие одного
актуального описания системы. Код, `AGENTS.md`, README, integration-документы,
локальный backend и knowledge base описывают разные стадии продукта. Это уже
привело к несовместимому real-контракту и заставляет ИИ-агента каждый раз читать
несколько взаимоисключающих документов.

Приоритетный порядок работ:

1. Выбрать канонический backend/audio-контракт и привести real-адаптеры к нему.
2. Исправить ложную маркировку demo-результата и передачу выбранной роли.
3. Стабилизировать `npm run check` и включить его в CI.
4. Сократить и переписать документацию как описание текущего состояния.
5. Удалить подтверждённо устаревшие копии спецификаций, архивные изображения и
   мёртвый CSS.

## Критические проблемы

### 1. [P0] У проекта нет единого канонического API-контракта

**Сложность: высокая.**

- Локальный `backend` на ветке `docker/dev` реализует `/v1/chat/*` и принимает
  при создании только `name` (`../backend/app/api/v1/routers/chat.py`).
- `../knowledge-base/backend/openapi.json` от 26.09 реализует `/v1/chats/*`,
  `case_uuid`, `/v1/chats/cases` и другую форму `CaseResponse`.
- Frontend вызывает `/v1/chats/*`, но его `CaseResponseDto` требует
  `first_role_preparations` и `second_role_preparations`, которых нет в
  knowledge-base; там одно поле `preparations`.
- Frontend отправляет `preparations` в `ChatCreateRequestDto`, а актуальная
  knowledge-base-схема этого поля в create request не содержит.
- Корневой `openapi.json` — ещё одна, более старая версия с `/v1/chat/*`.

Следствие: контрактные тесты проверяют вручную придуманные frontend fixtures, а
не совместимость хотя бы с одной из лежащих рядом спецификаций. Real-каталог
кейсов должен падать на парсинге knowledge-base-ответа.

**Что исправить:** сначала письменно определить владельца и источник истины
(генерируемая спецификация backend либо версия в knowledge-base). Затем
автоматически проверять frontend fixtures/парсеры против этой спецификации.
Старые копии удалить, а не оставлять с пометкой «не используется».

**Нужно решение владельца:** какая версия сейчас канонична — рабочая копия
`backend`, `knowledge-base` или развернутый `test-api`?

### 2. [P0] Публичный case DTO раскрывает скрытую информацию сценария

**Сложность: высокая (backend + frontend).**

`src/services/real/targetContract.ts:16-31` ожидает подготовки обеих ролей, а
парсер лишь выбрасывает их после получения. Это не скрывает данные: исходный
JSON уже виден пользователю в Network/DevTools. В knowledge-base поле называется
`preparations`, но также отдаётся публичным `GET /v1/chats/cases`.

Для тренажёра это позволяет заранее прочитать позицию AI-оппонента. Публичный
endpoint должен отдавать только публичное описание кейса. Скрытый prompt и
условия сторон должны оставаться на сервере и привязываться к сессии после
выбора роли.

### 3. [P0] Выбранная роль существует только в локальном UI

**Сложность: высокая из-за изменения API; frontend-часть низкая.**

`useStartNegotiation.ts:44` вызывает `createSession` без роли, а
`NegotiationClient.createSession` и `ChatCreateRequestDto` не имеют `roleId` или
`roleIndex`. Роль сохраняется только в localStorage snapshot. Backend не может
надёжно понять, за какую сторону играет пользователь, несмотря на обещание UI
«Вторая роль автоматически станет AI-оппонентом».

Добавить стабильный идентификатор роли в create-session contract, вернуть
фактически назначенные роли в session response и покрыть обе роли
интеграционным тестом.

### 4. [P1] Семантика transcript несовместима с audio-engine

**Сложность: средняя.**

`audio-engine-asyncapi.yaml` описывает `transcript.text` как завершённый текст
реплики. Frontend в `targetContract.ts:147-154` переименовывает его в
`transcript_delta`, а `useArenaAudio.ts:328-339` дописывает текст к текущему.
README также ошибочно утверждает, что это «очередная дельта».

При двух близких событиях одного speaker текст может склеиться или не совпасть
с сохранённой backend-репликой. Нужно сохранить тип `transcript`, заменять
текущий текст завершённым значением и синхронизировать тестовые fixtures с
реальной AsyncAPI. Если сервис должен отправлять дельты, менять нужно контракт и
сам audio-engine, а не только название во frontend.

### 5. [P1] `real/real/real` документирован как готовый, хотя результат остаётся mock

**Сложность: средняя для честного UI, высокая для настоящего результата.**

`BackendNegotiationClient.finishSession/getResult` всегда возвращает локальный
demo-result. При этом README называет комбинацию `real/real/real` реальными
чатами и голосовым audio-engine, а `AGENTS.md` вообще запрещает real-интеграции
вне auth. Нужно выбрать честную формулировку: например, «real chat + real audio,
но demo analysis», и не называть это полностью сквозным real-режимом.

## Ошибки логики и UX

### 6. [P1] Флаг demo-разбора передаётся наоборот и не описывает источник данных

**Сложность: низкая/средняя.**

В `ResultPage.tsx:33` передаётся `isDemo={isRealVoice}`. В mock-режиме
предупреждение скрыто, хотя анализ mock; в real voice оно показано, хотя имя
пропа означает обратное. При отсутствии `result.analysis` компонент в любом
режиме вызывает `createMockResultAnalysis`.

Нужно передавать происхождение результата (`mock`, `backend`, `fallback`) в
самом `NegotiationResult`, а не выводить его из аудиотранспорта.

### 7. [P1] Один `isRealVoice` смешивает независимые capabilities

**Сложность: средняя.**

`DomainServicesContext.tsx:13` объединяет negotiation source и audio source, а
затем этим флагом выбираются режимы UI, подписи demo и результат. Разрешённые
конфигурацией гибриды (`real/mock`, `mock/real`) ведут себя непредсказуемо.
Например, real negotiation client не поддерживает text turn, но при real/mock
UI предлагает текстовый режим.

Заменить флаг явными возможностями: `supportsText`, `supportsVoice`,
`resultOrigin`, `negotiationSource`, `audioSource`. Неподдерживаемые комбинации
отклонять при старте конфигурации или явно скрывать в UI.

### 8. [P1] Result page теряет реально выбранную роль

**Сложность: низкая.**

`ResultPage.tsx:24` берёт роли из статического `getDuelPreparation`, а не из
owner-scoped `readSessionPreparation`, который уже используется на Arena page.
Для второй роли подпись будет неверной, а для backend UUID станет
«Участник → AI-оппонент».

Прочитать snapshot на Result page и передавать его роли с приоритетом над mock.
Добавить сценарий: выбрать вторую роль → завершить → reload результата.

### 9. [P2] Debounced autosave теряет последнее изменение при быстром уходе

**Сложность: низкая.**

`usePreparationDraft.ts:23-34` на cleanup только отменяет 400 ms timer. Ввод и
немедленный Back/reload теряют последнее значение. Нужен flush актуального draft
на cleanup/pagehide и тест без ожидания статуса «Сохранено».

### 10. [P2] Прямой переход на landing hash зависит от скорости lazy chunk

**Сложность: низкая.**

`ScrollToLocation` находится вне `Suspense`; effect может выполниться до
появления `#problem`/другой секции и больше не повториться. Добавить scroll после
commit Landing page либо повтор после загрузки маршрута и e2e на прямой URL.

### 11. [P3] «Отправить повторно» является неработающей кнопкой

**Сложность: низкая.**

`ActivatePage.tsx:151` показывает сообщение о недоступности, но кнопка обещает
реальную отправку. До появления endpoint лучше сделать нейтральную подсказку или
disabled action с честной подписью.

### 12. [P2] Refresh token постоянно хранится в localStorage

**Сложность: высокая для полноценного исправления.**

`src/auth/storage.ts` сохраняет access и refresh token в читаемом JavaScript
хранилище. Любая XSS получает долгоживущую сессию; CSP в репозитории не
зафиксирована. Для прототипа это может быть сознательный компромисс, но сейчас
документация описывает механизм как инвариант и не фиксирует риск.

Предпочтительное production-решение — HttpOnly/Secure/SameSite refresh cookie и
короткоживущий access token в памяти. До backend-изменения добавить threat note,
жёсткую CSP на reverse proxy и запрет на вставку непроверенного HTML.

## Тесты и контроль качества

### 13. [P1] `npm run check` сейчас красный

**Сложность: средняя.**

Фактический прогон 27.09.2026:

- `typecheck` — прошёл;
- `lint` — прошёл;
- группа `real/mock/mock` — 56 passed, 2 failed;
- группа `mock/mock/mock` — 42 passed;
- общий результат — exit code 1;
- build, bundle report и performance smoke внутри `check` не запускались из-за
  предыдущей ошибки.

Падения:

1. `auth-resilience.spec.ts:666` — simultaneous bootstrap refreshes between tabs;
   Home heading не появился за 5 секунд.
2. `auth.spec.ts:243` — activation loading/success/error; success heading не
   появился после release mocked request.

Нужно расследовать гонки с clock/storage/route interception, а не просто
увеличивать timeout. До этого `check` нельзя считать merge gate.

### 14. [P1] В репозитории вообще нет CI workflow

**Сложность: низкая/средняя.**

В `.github` есть только инструкции Copilot. Ни typecheck, ни lint, ни tests, ни
build не выполняются автоматически на push/PR. Добавить workflow с Node из
`.node-version`, `npm ci`, кешем npm и разделёнными быстрыми/браузерными job.

### 15. [P2] Playwright-тесты не проходят TypeScript typecheck

**Сложность: низкая/средняя.**

`tsconfig.app.json` включает только `src`; `tsconfig.node.json` — только Vite и
Playwright config. Specs и harnesses проверяются ESLint и исполнением, но не
`tsc`. Добавить `tsconfig.test.json` с `noEmit` и включить его в `typecheck`.

### 16. [P2] Один медленный e2e-набор используется и как unit/integration tests

**Сложность: средняя.**

Контрактные парсеры, storage runtime и чистая бизнес-логика гоняются через
Playwright одним worker. Текущий полный браузерный прогон занял около 6.6 минуты
и запустил 100 сценариев. Крупнейшие specs: 785, 550 и 438 строк.

Вынести parser/storage/state-machine проверки в быстрый тестовый слой, оставить
Playwright для браузерных потоков и визуальных состояний. Разделить smoke и full
suite, чтобы агент мог быстро проверить локальную правку.

### 17. [P2] Contract tests воспроизводят frontend-модель, а не контракт сервиса

**Сложность: средняя.**

`tests/fixtures/serviceContracts.ts` и `service-contracts.spec.ts` импортируют
frontend parser и используют вручную написанные DTO. Именно поэтому зелёный тест
не заметил несовместимость с `knowledge-base/backend/openapi.json`.

Нужна проверка drift: генерация fixtures/типов из канонической спецификации или
хотя бы CI-скрипт, валидирующий используемые paths, required fields и enums.

## Документация и контекст для ИИ-агентов

### 18. [P1] `AGENTS.md` содержит прямые противоречия

**Сложность: низкая после продуктового решения.**

В одном файле одновременно сказано:

- стек включает Tailwind и MUI (`AGENTS.md:47-53`);
- Tailwind/MUI не входят в текущий stack (`AGENTS.md:99-103`);
- реальные API вне auth запрещены (`AGENTS.md:34-42`);
- в коде уже есть реальные negotiation и WebSocket clients.

Это наиболее вредный файл для агента, потому что он имеет приоритет над обычной
документацией. Оставить в нём только устойчивые правила и короткую карту
источников истины; текущее состояние продукта вынести в один актуальный документ.

### 19. [P1] `integration.md` и `docs/deployment-and-integrations.md` описывают старый код

**Сложность: средняя.**

Оба документа утверждают, что `BackendNegotiationClient`/`AudioEngineClient`
являются stubs, микрофон не захватывается и real negotiation/audio отсутствуют.
Текущий код реализует HTTP, WebSocket, AudioWorklet capture и playback.
`integration.md` датирован 23.09 и смешивает исторический план, текущий статус и
новый целевой API. Его 28 KB активно засоряют контекст и противоречат README.

Сохранить полезные невыполненные решения как короткий roadmap/ADR, а фактическую
схему переписать по коду. Не держать две почти одинаковые integration-статьи.

### 20. [P2] README неверно описывает стек и степень готовности

**Сложность: низкая.**

README называет Tailwind/MUI, которых нет в dependencies, и рекламирует
`real/real/real`, не объясняя mock-analysis и контрактный drift. Команды запуска
ориентированы на Bash (`cp`) при разработке в Windows/PowerShell.

Оставить в README: назначение, prerequisites, `npm ci`, запуск, поддерживаемые
режимы с точными ограничениями, ссылку на карту docs и одну команду проверки.

### 21. [P2] Документация тестов хранит быстро устаревающие числа вручную

`tests/visual/README.md` заявляет 82 сценария (51 + 31), фактически сейчас
запускаются 100 (58 + 42). Там же `npm run check` описан не полностью: package

Удалить ручные числа либо генерировать summary командой `--list` в CI.

### 22. [P2] `docs/future-website-structure.md` смешивает другой сервис и несуществующие routes

Документ содержит `/cases/:id/duel`, `/cases/:id/result`, `/settings`, `/admin` и

`/result/:sessionId`, а admin уже имеет отдельный `admin-frontend`.

Если это roadmap, назвать и явно отделить «не реализовано». Лучше перенести
межсервисное продуктовое видение в knowledge-base, а в frontend оставить только
реальную карту `docs/routes.md`.

### 23. [P3] Performance-документ является снимком измерений, а не устойчивой инструкцией

**Сложность: низкая.**

`docs/performance.md` содержит точные результаты одного дня и commit baseline.
Они быстро устареют. Инструкцию и budgets оставить в docs, а результаты конкретных
прогонов публиковать CI artifact или release note с commit SHA.

### 24. [P3] Инструкции для агентов продублированы

**Сложность: низкая.**

`.github/copilot-instructions.md` в основном повторяет `AGENTS.md`. Два набора
правил неизбежно расходятся. Сократить Copilot-файл до ссылки на `AGENTS.md` и
только GitHub-specific требований либо удалить, если платформа читает
`AGENTS.md` напрямую.

## Мусор и поддерживаемость

### 25. [P2] В Git лежит 32.37 MB архивных PNG

**Сложность: низкая организационно; средняя, если нужна миграция истории.**

Папка `examples/` — 27 файлов и примерно 96% размера отслеживаемого репозитория.
README папки называет их «архивными референсами landing», хотя там также auth,
home, preparation, result, duel и 404. Папка `lending` ошибочно названа
`lending`.

Если изображения нужны дизайнерам — перенести в Figma/knowledge-base/release
artifact или Git LFS. Если это одноразовые референсы уже реализованных экранов —
удалить из активной ветки. Не использовать их как visual baseline.

### 26. [P2] Корневые `openapi.json` и `integration.md` — подтверждённые stale-копии

**Сложность: низкая.**

Сам README говорит, что `openapi.json` не используется. Хранение заведомо
устаревшей спецификации рядом с кодом провоцирует агента выбрать её как источник
истины. После решения пункта 1 удалить файл и заменить ссылкой/скриптом получения
канонической версии. Аналогично объединить или удалить исторический
`integration.md`.

### 27. [P2] В `global.css` остались стили удалённого UI

**Сложность: низкая/средняя с visual smoke.**

`global.css:74-75,133-157` содержит `recommended-card`, `training-modal`,
`app-header`, `welcome-section`, `progress-card`, `catalog-section` и
`recent-section`, которых нет в текущем TSX. Это следы предыдущего Home UI,
смешанные с актуальными responsive rules.

Удалять по одному семейству, после каждого запуска `visual:smoke` и просмотра

global действительно оставался foundation/shared.

### 28. [P2] `landing.css` вырос до 3667 строк

Один файл размером около 72 KB затрудняет поиск владельца правила и занимает
лишний контекст агента. Компоненты landing уже разделены, поэтому стили можно
разнести по тем же секциям, сохранив один route entry и порядок импортов. Это

### 29. [P2] Соседний `front-end-mockup` выглядит как устаревшая грязная копия

либо удалить каталог.

### 31. [P2] История чатов загружается по схеме N+1

**Сложность: средняя/high с backend-изменением.**

`BackendNegotiationClient.listSessions` получает список, затем запрашивает detail
каждого чата (до четырёх параллельно). На длинной истории Home создаст десятки
запросов. Backend list response должен содержать достаточный summary (status,
case/name, created time), либо нужен отдельный paginated history endpoint.

### 32. [P3] Некоторые уже решённые архитектурные правила всё ещё записаны как временные запреты

**Сложность: низкая.**

Есть ADR о plain CSS, owner-scoped preparation storage, focus trap модального
окна, route splitting и отдельные service ports. Их не нужно заново объяснять в
нескольких файлах. Ссылки на ADR и краткого инварианта достаточно; детали лучше
оставить рядом с кодом и тестами.

## Предлагаемая минимальная структура документации

Чтобы не забивать контекст ИИ-агентов, оставить небольшой набор без дублирования:

| Файл | Единственная ответственность |
| --- | --- |
| `AGENTS.md` | Короткие обязательные правила, границы задачи, команды проверки, ссылки на источники истины. |
| `README.md` | Запуск, текущие поддерживаемые режимы, ограничения прототипа, навигация по docs. |
| `docs/architecture.md` | Composition root, auth/domain adapters, mock/real capability matrix. |
| `docs/contracts.md` | Ссылка на канонические спецификации и правила обновления; без копии OpenAPI. |
| `docs/routes.md` | Только фактически существующие routes и gates. |
| `docs/testing.md` | Быстрые проверки, full e2e, visual review, CI. |
| `docs/decisions/*` | Только принятые архитектурные решения. |

`auth.md` имеет смысл оставить как подробный документ сложного state machine.
`styling.md` можно оставить, но убрать дубли из `AGENTS.md`. Исторический roadmap
и будущую структуру всего продукта лучше держать в общей `knowledge-base`, а не
в frontend.

## Безопасный план очистки

1. Получить ответы на вопросы о каноническом контракте, статусе real-режима и
   судьбе `front-end-mockup`/`examples`.
2. Исправить P0/P1 runtime-проблемы и добавить contract drift check.
3. Стабилизировать два падающих теста; затем добавить CI.
4. Переписать `AGENTS.md` и README, объединить integration docs, удалить старый
   `openapi.json`, актуализировать routes/testing docs.
5. Отдельным коммитом убрать dead CSS; подтвердить визуально desktop/mobile.
6. Отдельным коммитом вынести архивные PNG и старый mockup, предварительно
   сохранив незакоммиченные данные.
7. После каждого этапа запускать быстрые проверки; после UI/CSS — полный
   `visual:smoke` и ручной просмотр релевантных PNG.

## Вопросы, без которых опасно делать окончательную чистку

1. Какой backend-контракт является каноническим: локальная ветка `docker/dev`,
   `knowledge-base/backend/openapi.json` или развернутый `test-api`?
2. Должен ли текущий frontend официально поддерживать real negotiation/audio,
   или эти адаптеры пока экспериментальны и default должен оставаться
   `real/mock/mock`?
3. Содержит ли `CaseResponse.preparations` секрет AI-сценария? Если да, его нужно
   срочно убрать из публичного endpoint.
4. Нужно ли сохранять 32 MB PNG из `examples/` в Git, и где находится их
   исходный дизайн (Figma/другой репозиторий)?
5. Можно ли архивировать `front-end-mockup` после сохранения его локального diff?
6. Планируется ли production auth в ближайшее время? От этого зависит приоритет
   миграции refresh token из localStorage в HttpOnly cookie.

## Что не следует «чистить» без причины

- `src/services/contracts` и разделение mock/real adapters полезны и уменьшают
  связанность.
- `docs/auth.md` подробно фиксирует нетривиальные race-condition инварианты; его
  лучше актуализировать, а не удалять.
- `scripts/performance-*`, budgets и route lazy-loading имеют практическую ценность.
- Owner-scoped preparation storage и modal focus management уже исправляют
  реальные классы ошибок; не откатывать их при упрощении.
- Игнорируемые `artifacts/` и `test-results/` нужны для диагностики, просто не
  должны коммититься.
