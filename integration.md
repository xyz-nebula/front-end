# Интеграция frontend, backend и audio-engine

Документ описывает целевую интеграцию «Арены переговоров» по состоянию репозиториев на 23.09.2026. Это план работ, а не описание уже работающей сквозной системы. Предлагается использовать существующий целевой контракт frontend (`README.md`, `src/services/real/targetContract.ts`) как основу и согласовать его с командами backend и audio-engine до включения real-режимов. Авторизация уже подключена к backend; переговоры и аудио пока работают только в mock-режиме.

## Что есть сейчас и где разрыв

| Контур | Фактическое состояние | Разрыв для сквозного сценария |
| --- | --- | --- |
| Frontend | Реальный auth/TOTP через `/api/v1/auth/*`; каталог, прогресс, переговоры, результат и голосовой сценарий на mock. `BackendNegotiationClient` и `AudioEngineClient` выбрасывают `feature-unavailable`. | Нет сетевых вызовов переговоров/WS и пути `микрофон → PCM → sendAudio`. UI продолжает показывать подписи «демо» и mock-прогресс. |
| Backend | FastAPI, Bearer auth, Postgres, Valkey; `/v1/chat/*` создаёт чат и отдельные сообщения, у сообщения есть `is_ai`, `sequence`. В моделях есть `Feedback`/`Judgement`, но нет публичного результата. | Нет переговорной сессии с `case_id`/`mode`, атомарного текстового хода, запуска/получения анализа, списка сессий, audio-ticket и внутреннего безопасного сохранения транскриптов. Публичный клиент сейчас может передать `is_ai: true`. |
| Audio-engine | `/v1/audio-stream` проксирует PCM-аудио в LocalAI и возвращает `audio_frame`. Токен из query декодируется как JWT с `chat_uuid`; AI-транскрипт отправляется в backend `/v1/chat/{chat_uuid}/message/` через общий Bearer token из окружения. | Нет одноразового ticket, проверки владельца/состояния сессии, сохранения пользовательского транскрипта, `transcript_partial` и `message_committed`. `pause`/`resume` игнорируются, ошибки LocalAI содержат сырой payload, секреты/токены печатаются в лог. |

При локальной разработке Vite сохраняет `/api` при proxy, а backend сейчас регистрирует маршруты как `/v1/*`. Между ними нужен явно проверенный rewrite `/api/v1/* → /v1/*` на reverse proxy либо соответствующая настройка backend. В backend `Caddyfile.dev` использует `handle_path /api/*` и удаляет префикс; `API_PROXY_TARGET` frontend следует направлять на этот gateway (например, `http://localhost:8080`), а не напрямую на порт 3000. В production нужен тот же маршрут и WebSocket Upgrade до audio-engine, доступный браузеру по WSS под HTTPS.

## Согласованный контракт до реализации

За основу берутся DTO и парсеры `src/services/real/targetContract.ts`: JSON на сети в `snake_case`, frontend-модели в `camelCase`. Защищённые HTTP-запросы идут с пользовательским Bearer access token через `/api`; после 401 frontend выполняет один refresh и один повтор. Backend отвечает ошибкой `{ "code": "...", "message": "...", "field": "..." }` (`field` необязателен). Все времена — ISO 8601 UTC, audio timestamp — Unix milliseconds. Источник истины для истории и результата — backend, а не WS и не локальное состояние.

| Операция frontend → backend | Целевой endpoint backend | Существенные поля |
| --- | --- | --- |
| Список кейсов | `GET /v1/cases` — согласовать как дополнение к текущему контракту | Стабильные `id`, название, описание, роль/цель/ограничения; IDs должны совпасть с существующими карточками. |
| Прогресс пользователя | `GET /v1/progress` — если сохраняется текущий блок прогресса | Число тренировок, средняя оценка, длительность и период расчёта; при отсутствии реализации frontend скрывает или явно маркирует демо-показатели. |
| Создать сессию | `POST /v1/negotiations` | `{case_id, mode: "text" \| "voice"}`; ответ: session. |
| Загрузить сессию | `GET /v1/negotiations/{id}` | `id`, `case_id`, `mode`, `status: active \| finishing \| finished`, `started_at`, `finished_at?`, `messages[]`. |
| Текстовый ход | `POST /v1/negotiations/{id}/turns/text` | `{text}`; один ответ с сохранёнными `user_message`, `ai_message`, `session_status`. |
| Разрешить голос | `POST /v1/negotiations/{id}/audio-ticket` | `{ticket, expires_at, protocol: "audio-engine.v1"}`. |
| Завершить и получить разбор | `POST /v1/negotiations/{id}/finish`, `GET /v1/negotiations/{id}/result` | `processing`, `failed` с `message` или `ready` с `result`. |
| История | `GET /v1/negotiations` | `id`, `case_id`, `mode`, `status`, `started_at`, `finished_at?`, `score?`. |

Каждое сохранённое сообщение: `id`, монотонный в пределах сессии `sequence`, `speaker: user | ai`, `text`, `created_at`. Результат: `session_id`, `outcome: victory | defeat`, `score: 0..100`, `summary`, `strengths[]`, `improvements[]`, `recommendations[]`. Командные запросы create/text-turn/finish используют `Idempotency-Key`; повтор после timeout обязан вернуть эффект исходной команды без второй сессии, второго хода или второго анализа. Для `finish` повтор с тем же ключом возвращает текущее состояние того же результата. Режим voice допускается только для voice-сессии, text — для text-сессии. Конкретные коды ошибок, HTTP-статусы и закрытия WS фиксируются в OpenAPI/AsyncAPI и контрактных тестах.

Голосовой протокол: browser открывает `wss://.../v1/audio-stream?ticket=...&protocol=audio-engine.v1`; backend выдаёт короткоживущий одноразовый ticket, привязанный к `user_id`, `session_id` и voice-mode. Параметр ticket и полный URL нельзя писать в логи. Входное событие — `audio_input` с `sequence`, `timestamp`, `format` и base64 `payload`; выходные — `transcript_partial` (полный текущий текст для `speaker`), `message_committed` (`event_id` и сохранённый backend `message`), `audio_frame`, `error` (`code`, безопасный `message`, `recoverable`) и `closed` (`code`, безопасный `reason`, `reconnect_allowed`). Формат входа и выхода: PCM signed 16-bit little-endian, mono, 24 kHz. При reconnect нужен новый ticket. `pause`, `resume`, `stop`, `close` должны иметь согласованное поведение. До разработки определить, что происходит с последней незавершённой voice-репликой при `finish`: предлагается дождаться её commit с коротким таймаутом и затем закрыть голосовой поток; при таймауте вернуть явную ошибку/состояние, не выдавать неполный анализ как готовый.

## Шаги backend

1. Закрепить OpenAPI переговоров, кейсов и прогресса рядом с фактическим FastAPI API. Согласовать с frontend обязательность полей, статусы, ошибки, границы текстового хода и таймауты анализа. Зафиксировать IDs и содержание кейсов; backend должен отдавать сценарий и инструкции AI из одного источника как для text, так и для voice, чтобы один кейс не вел себя по-разному. Для audio-engine предоставить защищённое внутреннее чтение контекста сессии/кейса после проверки ticket.
2. Добавить модель переговорной сессии, привязанную к `User`: `case_id`, `mode`, жизненный цикл `active → finishing → finished`, даты, результат и статус его обработки. `Chat`/`Message` можно использовать внутри, но публичный chat CRUD не является контрактом переговоров. Добавить миграции схемы БД вместо зависимости от `generate_schemas=True` для дальнейших изменений, индексы по владельцу/дате и уникальность `(session_id, sequence)`.
3. Реализовать перечисленные `POST/GET /v1/negotiations*`, `GET /v1/cases` и, для реального блока прогресса, `GET /v1/progress`: проверять владельца каждой сессии, её режим и допустимое состояние. Хранить ключи идемпотентности вместе с идентификатором пользователя, endpoint/сессией и отпечатком запроса; повтор с тем же ключом и другим payload отклонять. Список и история должны возвращать только сессии владельца.
4. Сделать текстовый ход одной серверной операцией: сохранить ввод пользователя, получить ответ AI с контекстом кейса и предыдущих сообщений, сохранить ответ и вернуть обе реплики. Запретить публичную запись AI-сообщения через `is_ai`; старый endpoint либо ограничить/убрать из публичного доступа, либо не использовать для переговоров. Разрулить конкурентные ходы и назначение `sequence` транзакцией/блокировкой, чтобы не было дублей и перестановок. Определить поведение при сбое AI: ход либо откатывается, либо сохраняется с явным состоянием для безопасного повтора; это должно быть отражено в API.
5. Реализовать выдачу и атомарное погашение ticket через общее с audio-engine хранилище (например, Valkey) или проверяемый внутренний endpoint. Ticket одноразовый, ограничен TTL, пользователем, сессией, режимом и версией протокола. Обычный пользовательский access token нельзя передавать audio-engine через query. Если audio-engine проверяет ticket через backend, внутренний endpoint должен быть недоступен браузеру и защищён сервисной авторизацией.
6. Добавить внутренний `POST /v1/internal/negotiations/{sessionId}/transcripts` для audio-engine: `{event_id, speaker, text, created_at}` → сохранённое сообщение с `id`/`sequence`. Проверять сервисную идентичность, session/ticket context и состояние сессии; `event_id` уникален для сессии и обеспечивает идемпотентность. Назначать sequence атомарно. Этот endpoint закрыт от браузера, а AI/user роль не берётся из публичного API.
7. Реализовать `finish/result`: остановить приём ходов, дождаться сохранения финального voice-транскрипта по согласованному правилу, поставить анализ в обработку и сохранить структурированный результат. Повтор `finish` не запускает анализ заново. `GET result` возвращает `processing/failed/ready` для обновления страницы и ограниченного polling. `Feedback`/`Judgement` сейчас содержат только текст и не заменяют требуемый result DTO.
8. Привести dev/prod routing к одному правилу `/api → backend /v1`, настроить TLS, доступ audio-engine к backend и Valkey, секреты вне репозитория, CORS только если frontend/API на разных origin. Добавить тесты владельца, режима, статусов, конкуренции, идемпотентности, ticket replay/expiry, transcript retry и результата после перезагрузки.

## Шаги audio-engine

1. Перевести WebSocket handshake с `?token=<JWT с chat_uuid>` на `?ticket=...`: сверять ticket через backend/общее хранилище, атомарно погашать, получать `user_id`/`session_id`/case context; отклонять чужой, повторный, истёкший и не-voice ticket. Убрать `SECRET`, `BEARER_TOKEN` и `chat_uuid` как текущую схему клиентской авторизации. Не логировать токены, payload JWT, URL и аудиоданные; убрать тестовый JWT из `templates/page.html`.
2. Обновить `audio-engine-openapi.yaml` и `audio-engine-asyncapi.yaml` до фактического единого протокола: `audio_input` с форматом, sequence и timestamp, все перечисленные исходящие события, политика ошибок и close codes. Текущие схемы описывают `type: audio`, `?token`, `audio_frame` и `auth_error`; они не совместимы с frontend DTO. Документация и код должны совпасть. Исправить порядок WebSocket handshake: текущая ветка ошибки пытается отправить текст до `accept()`, а отклонение должно происходить допустимым для ASGI способом и соответствовать документированному close code.
3. Валидировать размер, порядок, формат и rate входящих PCM-кадров; передавать их в LocalAI, контролировать backpressure и корректно освобождать соединения. Подтвердить, что LocalAI реально принимает/возвращает 24 kHz mono PCM s16le; если нет, добавить явное преобразование, а не менять поле `format` без обработки.
4. Настроить voice-сессию LocalAI контекстом выбранного кейса и ролью оппонента, полученными от backend по внутреннему каналу. Получать распознавание пользовательской речи и итоговый AI-транскрипт; сейчас код обрабатывает только `response.output_audio_transcript.*`, поэтому пользовательская реплика теряется. Передавать частичные тексты как полные snapshot-события `transcript_partial`.
5. Каждую финальную реплику обеих сторон сначала сохранить во внутреннем endpoint backend с устойчивым `event_id`, повторять запрос с тем же `event_id` после временного сбоя, затем отправлять браузеру `message_committed` с возвращёнными `id`/`sequence`. Если сохранение не удалось, не выдавать реплику как committed; сообщить безопасную recoverable ошибку и восстановиться по backend history. Убрать запись через `/v1/chat/{chat_uuid}/message/` и общий пользовательский Bearer token.
6. Реализовать реальные pause/resume (прекращение передачи/обработки микрофона и понятное поведение воспроизведения), stop/close и согласованные коды закрытия. При сбое LocalAI, backend или сети посылать стабильный код и безопасное сообщение без сырого ответа LocalAI. Ручное закрытие не должно провоцировать автоподключение; восстановимый обрыв допускает новый ticket и загрузку истории из backend.
7. Добавить контрактные и интеграционные тесты на handshake, формат, оба транскрипта, порядок `commit → message_committed`, повтор commit, reconnect и освобождение ресурсов; заменить ручные `test.py`/`back_post_test.py` воспроизводимыми проверками и согласовать контейнерную сеть с backend и LocalAI.

## Порядок совместной работы и критерий готовности

1. Команды утверждают OpenAPI/AsyncAPI, правило proxy, IDs кейсов, политику последней voice-реплики и close codes. Это единственные проектные решения, которые нельзя надёжно вывести из текущего кода.
2. Backend реализует session/text/result/ticket/внутренний transcript API; audio-engine подключает ticket и commit; frontend включает реальные адаптеры и capture. До готовности каждого контура соответствующий source остаётся `mock`.
3. Совместный smoke: пользователь входит, создаёт text-сессию, получает AI-ответ, завершает и открывает результат; затем создаёт voice-сессию, говорит, видит обе сохранённые реплики и слышит AI, обновляет страницу, продолжает после обрыва, завершает и снова открывает результат из истории. При тесте нет чужих сессий, дублей ходов/реплик или утечек токенов.

## Как общаются сервисы и что видит пользователь

1. Пользователь открывает frontend. Регистрация, активация, вход, refresh/logout и TOTP идут `browser → /api/v1/auth/* → backend`; backend возвращает access/refresh tokens. Пользователь видит экран входа, затем каталог кейсов и свою историю.
2. При выборе кейса frontend отправляет `case_id`/`mode` и `Idempotency-Key` в `POST /api/v1/negotiations`. Backend проверяет Bearer, создаёт сессию и отдаёт её ID. Browser открывает `/arena/{id}` и загружает историю `GET /api/v1/negotiations/{id}`. Пользователь видит условия кейса и диалог.
3. В text-режиме browser отправляет текстовый ход в backend. Backend собирает контекст кейса и историю, обращается к AI, атомарно сохраняет реплики и отдаёт их. Пользователь видит свой текст, индикатор ожидания, затем ответ оппонента; после reload — те же сохранённые сообщения.
4. В voice-режиме frontend сначала получает ticket от backend, затем открывает WebSocket с audio-engine. `Микрофон → PCM-кадры → audio-engine → LocalAI`; в обратную сторону `LocalAI → audio-engine → audio_frame → динамик`. Audio-engine отправляет финальные транскрипты пользователя и AI во внутренний backend API, получает сохранённые сообщения и только затем посылает `message_committed` в browser. Пользователь видит временный текст речи, затем подтверждённые реплики в диалоге и слышит голос AI. При обрыве frontend получает новый ticket, перечитывает историю и восстанавливает соединение по разрешённой политике.
5. При завершении frontend посылает `finish` в backend. Backend завершает приём новых реплик, формирует/сохраняет анализ и отвечает `processing`, позднее `ready` или `failed`; frontend ограниченно опрашивает `GET result`. Пользователь видит экран ожидания, затем оценку, итоги, сильные стороны, зоны роста и рекомендации либо понятную ошибку с повтором загрузки. История на `/home` берётся из backend и ведёт обратно к сессии или результату.
