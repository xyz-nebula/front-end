# Arena Negotiations — Agent Guide

## Project

**«Арена переговоров»** — AI-тренажёр переговоров.

Пользователь готовится к переговорному кейсу, проводит переговоры с AI-оппонентом и после завершения получает структурированный разбор своих действий от AI.

Проект создаётся в рамках хакатона. Сейчас основная задача репозитория — подготовить качественный frontend-прототип продукта.

## Current Stage

На текущем этапе реализуется **только frontend-макет без реальной бизнес-логики**.

Приложение должно работать полностью локально и визуально демонстрировать будущий пользовательский опыт.

Разрешено и желательно реализовывать:

* переходы между страницами;
* кнопки и интерактивные элементы;
* модальные окна;
* mock-данные;
* локальное состояние интерфейса;
* имитацию загрузки, переговоров, результатов и других состояний продукта;
* интерактивные сценарии, необходимые для демонстрации UX.

Не реализовывать без отдельного запроса:

* backend;
* базу данных;
* авторизацию;
* реальные API;
* интеграции с LLM;
* speech-to-text / text-to-speech;
* WebSocket-интеграции;
* серверное хранение данных.

Если функциональность можно убедительно показать через mock-данные — использовать mock.

## Tech Stack

* React
* Vite
* TypeScript
* Tailwind CSS
* MUI

Не добавлять новые библиотеки без реальной необходимости.

Перед добавлением крупной зависимости сначала проверить, нельзя ли решить задачу средствами текущего стека.

## Development Principles

### TypeScript

* Не использовать `any`.
* Использовать явные и понятные типы.
* Общие типы выносить в соответствующие файлы, если они переиспользуются.
* Не усложнять типизацию без необходимости.

### React

* Не создавать чрезмерно большие компоненты.
* Разделять UI на логичные переиспользуемые компоненты.
* Повторяющиеся элементы интерфейса выносить в общие компоненты.
* Не создавать абстракции ради абстракций.
* Состояние хранить максимально близко к месту его использования.
* Для mock-логики предпочитать простые решения.

### Project Structure

* Соблюдать существующую структуру проекта.
* Не перемещать и не переименовывать большое количество файлов без необходимости.
* Поддерживать понятное разделение страниц, компонентов, данных, типов и вспомогательной логики.
* Не дублировать одинаковый код и UI.

## UI / UX

Приложение должно корректно работать как на **desktop**, так и на **mobile**.

При создании интерфейса:

* соблюдать визуальную целостность между экранами;
* использовать единые отступы, размеры, радиусы и типографику;
* переиспользовать существующие UI-компоненты;
* предусматривать hover, active, disabled, loading и другие необходимые состояния;
* не оставлять очевидно неработающие элементы интерфейса, если их можно имитировать локально.

Финальный визуальный стиль проекта пока не зафиксирован.

Не принимай значимые продуктовые или дизайн-решения молча. Если задача требует:

* определения нового визуального направления;
* существенного изменения UX;
* изменения структуры приложения;
* добавления крупной библиотеки;
* изменения архитектурного подхода;

сначала кратко предложи решение и объясни его преимущества.

Мелкие UI-решения — размеры, отступы, расположение элементов, адаптивность и другие детали — можно принимать самостоятельно.

## Product Decisions

Не придумывай заранее полный набор страниц и функций продукта.

Реализуй только то, что требуется текущей задачей пользователя или уже существует в проекте.

Если есть несколько вариантов реализации, предпочитай тот, который:

1. лучше выглядит на демо;
2. проще поддерживать;
3. быстрее реализовать;
4. не создаёт лишней технической сложности;
5. можно позже подключить к настоящей backend/AI-логике без полной переделки frontend.

## Priority

Текущий приоритет:

**качественный, интерактивный и визуально убедительный frontend-прототип для демонстрации проекта на хакатоне.**

На этом этапе качество демонстрационного пользовательского опыта важнее построения production-ready инфраструктуры.
